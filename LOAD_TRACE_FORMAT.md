# Load Trace Format

This file defines the generated load trace used by the planned `baseload`
benchmark and by vcomp trace-loading experiments. The trace stores the key
sequence only. Values are generated by the loader with the same value generator
used by `fillrandom`.

## Generator

Use `tools/generate_load_trace.py`.

```bash
python3 tools/generate_load_trace.py /work/vcomp/load_traces/trace_500gb_1kb_u63.bin \
  --target-db-gb 500 \
  --key-size 24 \
  --value-size 1000 \
  --unique-ratio 0.6321205588 \
  --zipf-alpha 0 \
  --seed 12345678
```

For the 91B setup used in recent experiments:

```bash
python3 tools/generate_load_trace.py /work/vcomp/load_traces/trace_500gb_91b_u63.bin \
  --target-db-gb 500 \
  --key-size 48 \
  --value-size 43 \
  --unique-ratio 0.6321205588 \
  --zipf-alpha 0 \
  --seed 12345678
```

`--target-db-gb` computes the record count as:

```text
num_records = target_db_gb * 1024^3 / (key_size + value_size)
```

This matches `experiments/scripts/load/load.sh`.

## Binary Layout

All integer and floating-point fields are little-endian.

### Header

The header is 88 bytes.

| Offset | Type | Name | Description |
| --- | --- | --- | --- |
| 0 | char[8] | magic | ASCII `VLOADTR1` |
| 8 | uint32 | version | Format version. Current value is `1` |
| 12 | uint32 | header_size | Header bytes. Current value is `88` |
| 16 | uint64 | num_records | Number of records in the body |
| 24 | uint64 | key_domain | Key ids are in `[0, key_domain)` |
| 32 | uint64 | unique_count | Exact number of distinct keys in the trace |
| 40 | uint32 | key_size | Intended RocksDB `--key_size` |
| 44 | uint32 | value_size | Intended RocksDB `--value_size` |
| 48 | double | unique_ratio | `unique_count / num_records` |
| 56 | double | zipf_alpha | Repeat-key skew parameter |
| 64 | uint64 | seed | Generator seed |
| 72 | uint64 | flags | Bit flags |
| 80 | uint64 | reserved | Must be zero |

Current flags:

| Bit | Name | Meaning |
| --- | --- | --- |
| 0 | exact_unique_count | The stream has exactly `unique_count` distinct keys |
| 1 | affine_key_mapping | Dense ranks were mapped into `key_domain` by an affine permutation |

### Body

The body is `num_records` repetitions of:

| Type | Name | Description |
| --- | --- | --- |
| uint64 | key_id | Logical key id for one put operation |

The loader should materialize `key_id` with the same path as `fillrandom`:

```text
GenerateKeyFromInt(key_id, key_domain, key)
value = RandomGenerator.Generate(value_size)
Put(key, value)
```

## Semantics

`unique_ratio` controls the final number of distinct keys. The generator
guarantees the exact `unique_count` by introducing new keys gradually and using
repeat operations for the rest.

`zipf_alpha` controls repeat-key skew. `0` means uniform repeats over already
introduced keys. Larger values bias repeats toward lower ranks. The generated
key ids are then permuted over `key_domain`, so the byte-key order is not just
monotonic insertion order.

The default `unique_ratio` is `1 - exp(-1) ~= 0.6321`, matching the expected
unique-key rate of RocksDB `fillrandom` when it draws `N` random keys from a
domain of size `N`.

## Validation

A valid trace must satisfy:

```text
file_size == header_size + 8 * num_records
magic == VLOADTR1
version == 1
unique_count <= min(num_records, key_domain)
```

The generator also writes a JSON sidecar next to the trace by default:

```text
<trace>.meta.json
```

The sidecar is for inspection only. Loaders should rely on the binary header.
