# F2Load 깊은 레벨 coverage 붕괴 — 원인과 수정 (2026-09-13)

## 증상
baseline 대비 F2Load의 per-level key-range coverage가 L3/L4에서 무너진다.
1 TB E4-64m4: L4 81.5→37.8, L5 85.1→55.7. P0: L3 87.5→71.8, L4 97.0→86.4.
filter check per lookup이 baseline 2.11–5.11 범위인데 F2Load는 2.42–3.68로 압축되는 직접 원인.
100 GB 이하에서는 거의 재현되지 않고(E4 100 GB: L4 63.0 vs 72.8), 1 TB에서 뚜렷하다.

## 기각된 가설
- intra-L0 compaction 비활성화(b53e2a4a45): 되살려도 coverage 65.23→65.26. vcomp에선 L0가 안 쌓여
  62건만 발생(baseline 378건). 원인 아님. (`VCOMP_INTRA_L0=1` 게이트로 남아 있음)
- picker sweep 순서: baseline과 동일(평균 |Δ위치|/도메인 0.225 vs 0.196, 전진비율 0.645 vs 0.634).
- materialization: 가상 상태와 실체화 후 key range 완전 일치. 무죄.

## 원인
`DBImpl::RefillVirtualL0WindowLocked`는 **가시 L0 바이트만** 보고 다음 배치를 넣는다. 창 크기 기본값은
`max_compaction_bytes` = 25 × `target_file_size_base` = 1600 MiB로 레벨 타깃과 무관하게 고정.
Phase 1이 L0 파일을 version에 직접 등록해 write path를 우회하므로 baseline의 write stall
(`level0_slowdown/stop_writes_trigger`, `soft/hard_pending_compaction_bytes_limit`)이 전혀 작동하지 않는다.

`level_compaction_dynamic_level_bytes=false`에서 L0 score = max(파일수/trigger, L0바이트/L1타깃)
(version_set.cc:4018). 1600 MiB 창이면 E4는 25, P0는 6.25. 피드가 공짜라 compaction 풀이 항상 포화이고,
포화된 score 스케줄러는 모든 레벨을 L0 score 근처에서 평형시킨다. 실측 L1 팽창 23.8× / 6.2×.
backlog는 상한이 없어 데이터셋이 클수록(E2 축), 레벨 타깃이 작을수록(E4/E5 축) 커진다.
마지막 `waitforcompaction`이 이 backlog를 한꺼번에 몰아 내리면서 key 공간에 덩어리진 레이아웃이 남는다.

## 수정 (`VCOMP_L0_BACKPRESSURE`, db_impl_compaction_flush.cc `pressure` 람다)
mode 3 = baseline의 stall 의미론 그대로: `level0_stop_writes_trigger` 또는 `hard_pending_compaction_bytes_limit`
이면 피드 **정지**, `level0_slowdown_writes_trigger` 또는 `soft_pending_compaction_bytes_limit`이면 **한 파일씩만 admit**(감속).
mode 4가 실패했으므로 실제로 일하는 조건은 pending bytes. 설정 스윕 어느 축에서도 별도 튜닝 없음.

## 후속 분석 (2026-09-13 20:40): YCSB C 처리량 격차의 나머지 절반 — 최상위 레벨 파일 폭
E5-256은 수정 후에도 baseline 949k vs F2Load 1.61M ops/s (구조·SST 수·SST read/op는 일치). 원인:
- `db.get.micros` 평균 49.7 vs 29.0 µs가 격차 전부(48 스레드 ÷ 평균 = ops/s).
- filter probe는 전부 block-cache hit인데 baseline이 Get당 0.84회 더 많고, 그 0.84회에 20 µs가 든다(정상 ~1 µs).
- baseline E5-256의 L1은 파일 **1개**(L1 타깃 = 256 MiB = SST 1개)가 도메인의 **78%**를 덮는다. 모든 Get이 L1을 지나므로
  lookup의 78%가 같은 filter 블록의 캐시 핸들 하나에 몰려 LRU shard 락 경합 → Get당 +20 µs.
- 같은 패턴: 수정 전 P0 F2Load도 L1 파일 하나가 81%를 덮었고 Get 평균 50.7 µs / 929k. 최상위 파일이 ≤5%인 셀은 전부 ~30 µs / 1.5–1.6M.
- `cache_index_and_filter_blocks=false`(캐시 핸들 경유 없음)로 E5 baseline 재측정: 984k → 1.26M (체인과 동시 실행이라 하한값; 정밀 2x2는 fix_20260913_ab_cache_clean).
- 장치 읽기 지연(4 KB O_DIRECT 랜덤, mean 67.6 µs)과 단편화는 양쪽 동일 — 물리 배치 가설 기각. 측정 중 compaction 0, 동시 로딩 없음.
- filter/read 지표는 Σ(레벨별 coverage) × 0.92–0.99로 완전히 결정된다(8셀). 따라서 최상위 레벨의 파일 폭(로딩 종료 시점의 우연)이
  filter/read와 처리량 둘 다를 흔든다. 수정 전 P0 −37%의 상당 부분도 backlog가 아니라 이 효과였다.
시사점: YCSB C 처리량·filter/read를 fidelity 지표로 쓸 때 최상위 1–2레벨은 run 간 우연이 지배한다(baseline P0 r1–r3의 L1 dom coverage 7–14%, E5-256은 78%).
L3 이상 coverage·SST 수·compaction bytes가 로딩 구조를 반영하는 지표.

## p99 격차(baseline ~166 vs F2Load ~110 µs, 전 쌍 공통)의 원인 — 물리 배치 (09-14 06:10)
- SST 테이블 속성은 동일(P0·E5-sst16 쌍: 블록 4,136 B, index/filter 크기, fmt 7, index 타입). materialization은 `open_options_` 그대로 사용.
- RocksDB 블록 읽기를 모사한 8 KB O_DIRECT 랜덤 읽기(파일 24개×200회): P0 baseline mean 80.0 / p99 **133.6 µs**, P0fix F2Load 72.3 / **91.1 µs**.
  4 KB 정렬 읽기로는 차이가 없었음(67.6 µs 양쪽) → 페이지 경계를 걸치는 읽기에서만 차이.
- 첫 extent가 1 MiB(md0 chunk) 경계에 정렬된 파일 비율: baseline **38%**, F2Load **100%**. compaction이 여러 출력 파일을 동시에 쓰며
  할당이 끼어들어 정렬이 깨지고, 8 KB 읽기가 chunk 경계를 넘으면 장치 I/O 2회 → 꼬리 2배.
- Get 평균에는 0.22 reads/op × ~8 µs ≈ 2 µs 영향. 평균 latency·처리량 지표에는 미미, p99 지표에는 구조적 차이.
- 시사점: F2Load의 materialized 파일은 "너무 깨끗"하다. 실제 배포 DB는 compaction으로 쓰여 baseline 쪽 배치를 가진다.
  p99 fidelity를 주장하려면 materialization의 할당 패턴을 흉내내거나(예: 워커 간 인터리브 쓰기) 한계로 명시해야 한다. 계획의 읽기 지표(평균 latency)에는 해당 없음.

### filter checks per lookup — 레벨별 분해 (uniform 딥카피, PERF_CONTEXT bloom_filter_useful+full_positive @level)
표: experiments/results/filter_checks_per_level_uniform_260914.tsv
- **L3 이상 probe 합: 15쌍 중 12쌍 |Δ| ≤ 0.05 probes/Get, 중앙 −0.009.** 깊은 레벨 구조는 filter 지표로 봐도 baseline과 일치.
- 총 filter/read 편차(−0.55 ~ +0.54)는 **전부 L1–L2**에서 나온다. L1·L2는 레벨 크기 256 MiB/2.5 GiB로 파일 수십 개, 로딩 종료 시점의 잔여 파일 폭이 run마다 달라 baseline replicate 사이에서도 같은 크기로 흔들린다(P0 r1–r3 L1 dom 7–14%, E5-256 r1/r2 78/25%).
- 예외 E4-256m4: L3 0.66→0.75, L4 0.77→0.82 (L3+ +0.13). multiplier 4에서만 깊은 레벨 coverage가 F2Load 쪽이 높다 — 유일한 설정 고유 잔여, 원인 미확인.
- 논문 지표 권고: "filter checks per lookup"을 총합과 함께 **L3+ 합**(구조 지표)과 L1–L2(엔드게임 노이즈)로 나눠 보이거나, baseline replicate 밴드를 병기.
